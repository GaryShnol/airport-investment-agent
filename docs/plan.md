# Build plan (read when starting a step; not auto-loaded)
Task status lives in `TASKS.md`. This file holds the design.

## Configuration (no hardcoded values)
- `.env` (see `.env.example`) -> `src/config.py` `Settings.from_env()`: `LLM_PROVIDER`, `LLM_MODEL`, `LLM_BASE_URL`, `LLM_TEMPERATURE`, `OPENAI_API_KEY`, `OLLAMA_BASE_URL`, `OLLAMA_NUM_CTX` (Ollama context window; unset = server default), `CENSUS_API_KEY`, `DB_PATH`, `SEED_DB_PATH` (gzipped seed written by `src.seed`), `SEED_MAX_MB`, `SEED_DB_URL`, `SEED_DB_SHA256` (optional), `BOOTSTRAP_CHECK_TIMEOUT_S`, `APP_PORT`, `RAW_DATA_DIR`, `WEIGHTS_PATH`, `LOG_LEVEL`, `MAX_INPUT_CHARS` (input guard for the agent), and for ingest only the upstream endpoints `CENSUS_API_URL`, `CENSUS_GEOCODER_URL`, `ONTIME_PREZIP_URL` (with `{year}` and `{month}`), `T100_PAGE_URL` (defaults in `src/config.py`), `HTTP_TIMEOUT_S` (per request) and `GEOCODER_DELAY_S` (pause between Geocoder requests). Secrets are hidden from `repr`. Relative paths resolve against the project root.
- `config/weights.yaml` -> `load_scoring()` validates (weights sum to 1) and returns `ScoringConfig`: weights, congestion sub-weights, long-haul miles, `max_ranked` (longest ranking a tool returns), minimum long-haul share and sensitivity list, min passengers, `min_ontime_flights`, target load factor, sensitivity runs/jitter/seed, Census dataset, variable, vintage, growth base vintage and Geocoder vintage (`census`), regions, metro aliases (ambiguous names such as LA, with the default airport).
- Why split: env is per-deployment and secret; methodology is reviewable, versioned and part of the design doc.

## LLM provider
`src/llm.py`: `PROVIDERS = {"openai": ..., "ollama": ...}`; `get_chat_model(settings)` returns a LangChain `BaseChatModel`. Lazy imports. `LLM_BASE_URL` is the server URL for either provider (`OLLAMA_BASE_URL` remains the Ollama fallback). `llm_error_message(settings, exc)` turns a missing key, an unreachable server, a rejected key or an unknown model into one line naming the `.env` setting to fix; the app and the CLI show it instead of a traceback. `.env.example` defaults to OpenAI (the reviewer quickstart needs only the key); a local Ollama model is the optional development path. `openai` accepts `LLM_BASE_URL` for any OpenAI-compatible server (Ollama `/v1`, LM Studio, vLLM). No class hierarchy: LangChain already provides the common interface. Local models are weaker at tool calling, so tools are few, typed and return small JSON; the agent is tested with a fake model too.

## SQLite schema
- `meta(source, last_period, upstream_latest, checked_at, fetched_at)`  one row per source (freshness summary)
- `ingest_log(source, period, rows, loaded_at, file_hash, source_rows)`  one row per loaded (source, month); makes ingest idempotent. `rows` = rows inserted; On-Time also stores the file's sha256 (`file_hash`) and the flights read (`source_rows`, used for the row-count check)
- `airports(iata, name, state, region, cbsa, lat, lon, municipality)`  municipality = city served, used by `resolve_airport`; `cbsa` copied from `airport_cbsa` after every ingest (the airports reload resets it)
- `airport_cbsa(iata, lat, lon, cbsa, cbsa_name, kind, geocoder_vintage, geocoded_at)`  Census Geocoder cache: the CBSA the airport's coordinates fall in (`kind` metro or micro; null = outside every CBSA)
- `t100_route_month(origin, origin_state, dest, year, month, config, distance, departures, seats, passengers)`  origin_state = ORIGIN_STATE_ABR (peer-set filter)  config = pax | cargo | combi | unknown
- `ontime_airport_month(airport, year, month, dep_flights, dep_del15, dep_del15_n, dep_cancelled, taxi_out_sum, taxi_out_n, arr_flights, arr_del15, carrier_min, weather_min, nas_min, security_min, late_aircraft_min)`  departure side at the origin airport; arrival side and cause minutes at the destination airport. Counts, not rates. `dep_flights` = scheduled departures incl. cancelled (cancellation rate denominator); `dep_del15_n` = departures reporting DEP_DEL15 (delay-rate denominator: 4,285 cancelled flights in 2025 still report one); `arr_flights` = arrivals operated (ARR_DEL15 reported, so not cancelled or diverted), the denominator for NAS minutes per arrival
- `census_metro(cbsa, year, population, fetched_at, name)`  one row per CBSA (metropolitan or micropolitan area) and vintage; `year` = ACS 5-year vintage (its last year), `name` as the API returns it

## Ingest (offline, idempotent, `src/ingest.py`)
- Reads files from `RAW_DATA_DIR`; skips (source, month) already in `ingest_log`; validates ZIPs with `zipfile`; aggregates On-Time in a stream with `usecols`.
- On-Time: `RAW_DATA_DIR/ontime/**/ontime_*.zip`, one BTS TranStats monthly download per file (`T_ONTIME_REPORTING.csv`, upper-case column names such as `DEP_DEL15`, `TAXI_OUT`, `NAS_DELAY`), read from the ZIP in chunks. A file whose sha256 is already in `ingest_log` is skipped unread; a new or changed file replaces its month only. The summary prints flights read vs the acceptance counts, the cancelled-flight handling and On-Time airports with no `airports` match. The PREZIP files (`On_Time_Reporting_Carrier_On_Time_Performance_...`) use different, CamelCase column names and are not read yet (P4.6).
- Census (`src/census.py`, `ingest_census`): population (`census.variable`, B01003_001E) of every CBSA from the Census Data API (`census.dataset`, ACS 5-year) for `census.vintage` and `census.base_vintage`. Idempotent: a vintage in `ingest_log` (source `census`, period = vintage) is never requested again. All needed vintages are fetched before anything is written, so an API error writes nothing; the API answers a missing or invalid key with HTTP 200 and an HTML page, so the body is checked too. `meta` (source `census`): `last_period` = latest vintage loaded, `fetched_at` = retrieval date. Census never moves the analysis window (`store.WINDOW_SOURCES` = t100, ontime). The key (`CENSUS_API_KEY`, required by the API) goes in the query string and is never printed: errors report the exception type, not the URL. Without a key the step is skipped with a message. The attribution ("This product uses the Census Bureau Data API but is not endorsed or certified by the Census Bureau.", `census.ATTRIBUTION`) is printed by ingest and shown in the sidebar and the README.
- Airport -> CBSA (`geocode_peer_airports`): the Census Geocoder (`geographies/coordinates`, benchmark and vintage from `census` in the YAML) for peer-set airports only (`scoring.in_peer_set`), from `airports` lat/lon. Cached in `airport_cbsa` per Geocoder vintage and coordinates, "no CBSA" included, so a rerun makes no request; requests are spaced by `GEOCODER_DELAY_S`; a failed request is reported and not cached (retried next run), and after 5 failures in a row the rest wait for the next run. Ingest prints matched airports, the airports with no CBSA and the failures. An airport gets the CBSA it sits in, which is not always the city it is named after.
- `--check` (`src/upstream.py`): per loaded source, the latest period upstream. On-Time: HEAD the PREZIP URL for each month after the loaded one up to today, until a 404 (200 with a ZIP = published). T-100: the "Latest Available Data: <Month YYYY>" label on the BTS download page; a missing or unreadable label = unknown. Census: the newest vintage of `census.dataset` whose variable metadata exists (no key needed). Stores `upstream_latest` (null = unknown) and `checked_at` in `meta` and prints loaded vs upstream per source. Any network failure or unexpected answer gives unknown, never an error. No downloads; never runs at chat time (tools only read `meta`).
- Freshness (`store.source_freshness`, `store.overall_freshness`): per source "fresh" (upstream has nothing newer), "stale (upstream has YYYY-MM)" (a vintage YYYY for Census) or "unknown" (never checked, or the check could not tell). Overall: stale if any source is stale ("stale (upstream has 2026-07 for ontime, 2026-07 for t100)"), else unknown if any is unknown, else fresh. Every envelope carries it; when stale, a warning is added to the assumptions and the answer still uses the loaded data. `data_status` lists each source with its state, loaded period and check time.
- Optional (stretch): `--download` fetches missing On-Time months (direct URLs) and T-100 (form POST). Any failure falls back to local files.
- Seed DB (`src/seed.py`, `python -m src.seed build`): copies the schema tables (aggregates, reference tables, `meta`, `ingest_log`; no raw files) from `DB_PATH` into a fresh DB stamped with `store.SCHEMA_VERSION` (`PRAGMA user_version`), VACUUMs it and writes `SEED_DB_PATH` (gzip) plus `<file>.sha256` (`sha256sum` format). Stops, writing nothing, if the compressed file exceeds `SEED_MAX_MB`. Not committed: published as a GitHub Release asset.
- Bootstrap (`src/bootstrap.py`, the container entrypoint): if `DB_PATH` is valid (`store.db_problem`: schema version matches, every schema table non-empty) nothing happens; otherwise it downloads `SEED_DB_URL`, checks the sha256 (`SEED_DB_SHA256`, else the sibling `.sha256` file), decompresses to a temp file in the DB folder, validates it and moves it into place with `os.replace`. An invalid existing DB is kept as `<name>.invalid`. Any failure removes the temp files and exits with the three options (set `SEED_DB_URL`, mount a DB, run ingest), no traceback; only the URL's host and path are printed. Then `ingest --check` with `BOOTSTRAP_CHECK_TIMEOUT_S` per request; any failure = freshness unknown.

## Tools and envelope (6 tools)
`data_status`, `resolve_airport`, `airport_metrics`, `compare_airports`, `rank_airports`, `explain_demand_gap`.
Every tool returns:
```json
{"headline": "43.2% of all departures from ANC (incl. cargo) are >= 2,500 mi (37,969 of 87,988); passenger service: 11.5% (...)",
 "facts": [{"label": "Long-haul share >= 2,500 mi, passenger service", "value": "11.5%", "required": true}],
 "data": {}, "data_period": "2025-01..2025-12", "freshness": "fresh|stale (upstream has 2026-07 for ontime)|unknown",
 "assumptions": ["long-haul >= 2500 mi", "passenger flights only"], "confidence": "high|medium|low"}
```
- `headline`: one deterministic sentence with the answer, built by the tool (errors: the message). Rendered above the facts card; for long haul it states the threshold and both bases with departure counts. The model comments on it and must not restate it: `drop_restated_headlines` (src/agent.py) removes verbatim copies from the commentary.
- `facts`: pre-formatted, human-readable strings the model copies instead of reading `data`. Required for every tool: data period and confidence. `airport_metrics` depends on its `topic` (`long_haul`, `demand`, `growth`, `all`; default `all`), which decides both the rows returned and the required ones: `long_haul` returns and requires the threshold, both long-haul shares (all flights and passenger service) and the sensitivity at each other configured threshold, plus the departure counts; `demand` returns passengers, seats, departures and load factor (passengers and load factor required); `growth` returns passengers in both windows and the growth (growth required); `all` returns and requires the union. A passenger question therefore shows no long-haul rows. The data period is always a required fact. `rank_airports`: the weights used, as one string. Component labels say what they measure ("scale (annual passengers)").
- `ensure_facts` (src/agent.py), applied after `<think>` stripping: every required fact must appear in the answer, else a short "Key figures (from the data tool)" block lists only the missing ones. No retry loop. Matching: a period needs only its year(s); a word (confidence) must appear as is; numbers match exactly (trailing zeros ignored, decimal comma accepted), values above 10 also as the nearest integer (half up), values below 1 also as a percentage (0.385 = 38.5); date tokens such as 2025-12 in the answer never count as numbers. Mandatory content is therefore guaranteed by code, not by the prompt.
- `rank_airports` exposes only `weights_used` (configured weights are in `data_status`): showing both made small models mix them.
- `airport_metrics(airport, threshold_mi, topic)`: `airport` is a code or a name, resolved like `resolve_airport` (a name states the definition used as the first assumption; an ambiguous name returns `ambiguous` with the best match and the alternatives instead of data; no match returns the explicit no-match envelope), so one call answers a single-airport question. Volume, load factor, growth, long-haul share with and without cargo plus sensitivity at each configured threshold, congestion, filtered by topic. Topic `congestion` returns and requires departures delayed >= 15 min, mean taxi-out, NAS-delay minutes per arriving flight and cancelled departures (marked not scored), plus the On-Time flights reported and the congestion percentiles; without usable On-Time data one required fact says why (not loaded, no flights of the reporting carriers, or below `min_ontime_flights`). `all` includes it.
- `compare_airports(a, b)`: both names resolved like `resolve_airport`; a configured metro alias uses its default and states it (LA = LAX), any other ambiguity or no match is returned as is. Side by side (two-column table in `render.py`, one column per airport plus a verdict column): delayed departures, taxi-out, NAS delay per arrival, cancellations (shown, not scored), congestion percentile (On-Time); load factor, passengers, growth, long-haul share (T-100). Significance: each On-Time figure carries a margin of error at `comparison.confidence_level` (0.95): rates from the flight counts (normal approximation, z * sqrt(p(1-p)/n)), minute averages from the spread of the monthly means (z * sd / sqrt(months); only monthly sums are stored). Verdict: if |a - b| <= sqrt(margin_a^2 + margin_b^2) the headline says "no meaningful difference in X", otherwise it names the higher airport; missing figures are "not comparable". T-100 figures count every flight, so they are compared as is ("higher (full count)"); the congestion percentile is a rank and is not tested. The headline ends with an overall sentence from the verdicts of the scored measures only (delayed departures, taxi-out, NAS delay per arrival; `scoring.overall_verdict`): "no meaningful difference" when none differs, "X is higher on every measure with a meaningful difference" when every comparable measure points the same way, "not comparable" when none can be compared, else "mixed, no airport is higher on every measure". When one airport has more than `comparison.size_ratio_note` (3) times the other's passenger-service departures, a note says so (rates compare per flight; the airports differ in scale). Facts carry an `airport` key (values) or a `metric` key (verdicts), used by the table and by the figure check.
- `rank_airports(region, top_n, sort_by, weights)`: scores, component breakdown, weights, rank stability (see Scoring), and drivers: for each ranked airport its strongest and weakest component by national percentile (`scoring.drivers`; ties go to the component listed first in the weights; a component on the tie floor, i.e. the lowest value in the peer set shared by several airports such as no material long haul at percentile 43, is never the strongest, see `scoring.tie_floor`), as `Drivers: <IATA>` facts and a Drivers table under the ranking, so "why is PWM fourth?" is answered by the card, not by the model. `sort_by` (score, growth, load_factor, passengers) reorders in code and keeps each airport's score rank. `weights` is a scenario override: keys must be weight names from `config/weights.yaml`, values non-negative; keys not given keep the configured weight; all are renormalized over the built components. The envelope is labeled `mode: scenario`, shows the scenario and base weights, and the base rank next to the scenario rank. The list is capped at `max_ranked` (YAML).
- `explain_demand_gap(airport)`: a labeled PROXY (headline starts "PROXY, not a measurement"; required fact "Unmet demand: not observable"). Unmet demand cannot be observed in T-100 (it counts passengers carried, never passengers turned away); measuring it needs booking, fare and spill data, which the assumptions say. Facts, all in code: months whose airport-wide load factor exceeds `unmet_demand.target_load_factor` (0.80) and the `peak_months` highest; the `top_routes` routes by passengers (with load factor) and by passengers above the target; the spill proxy = the number of passengers above the target load level, i.e. passengers in excess of target x seats, summed over the route-months above the target (a route-month at 85% adds 5% of its seats; it is not the number of passengers on full flights), with its share of passengers and the range over `target_sensitivity` (0.75-0.85); the delay-cause mix (shares of NAS, carrier, late-aircraft, weather and security minutes, arrival side); growth. A "why" list is built only from these facts (months above target and peaks, the routes carrying most of the proxy, the largest delay cause, growth) and rendered under the card. Confidence is capped at medium.
- `resolve_airport(text)`: configured metro alias (ambiguous, with a default: LA = LAX), then exact IATA (wins outright), then name or city, ranked by passengers in the window ("New York" puts JFK ahead of "New York Stewart"); name and city matches count only airports with passenger service. Several matches return `ambiguous` with the `best` match and the `alternatives` (the agent asks which one). No match returns an explicit required fact ("no match for ...") with suggestions (closest names by difflib ratio) or a hint, never an empty result.
- Regions: a region not in `config/weights.yaml` (e.g. California) returns a deterministic message listing the configured regions with their states and suggesting `region='national'` (every US airport in the peer set) or a specific airport.
- Errors come back as an envelope with `data` null, `error` and `candidates`; tools never raise to the model. Lists are capped (`MAX_LISTED`) to fit short local-model contexts.

## Definitions (fixed; used by ingest, scoring and tools)
- Passenger service: T-100 rows with AIRCRAFT_CONFIG 1 (passenger) or 3 (combi) and DEPARTURES_PERFORMED > 0. Cargo (2) and undocumented (4) are excluded from passenger metrics; they count only in "all flights" figures.
- Peer set: airports with a US state or territory (`airports.state`, from OurAirports) and at least `min_passengers_per_year` passenger-service passengers in the window (100,000). Passengers, not departures: a departure floor admitted 9-seat commuter airports (Block Island, Westerly: about 20k passengers) and left out regional airports such as ORH and PSM. Percentiles are computed inside this set. T-100 `ORIGIN_STATE_ABR` is not used for this: it also holds Canadian province codes (YYZ = ON) and TT for the Pacific territories.
- Window: trailing 12 complete months ending at `min(last_period)`; growth compares with the previous 12. Coverage of the previous 12 months is checked only for T-100 (`store.GROWTH_SOURCES`): On-Time is used only inside the window, so its missing 2024 must not switch growth off.
- On-Time sides: departure delay rate, taxi-out and cancellations belong to the origin airport. Arrival counts and delay-cause minutes belong to the destination airport, because BTS records delay causes for arrival delays.

## Scoring (`src/scoring.py`, pure functions, unit-tested)
Component = percentile inside the peer set; airports are ranked inside the requested region afterwards. Raw values are always shown next to the percentiles.
- Utilization = pax / seats (passenger service)
- Scale = annual passengers (passenger service)
- Congestion = sub-metrics from On-Time: departure-delay >=15 rate (among departures reporting DEP_DEL15), mean taxi-out (origin side), NAS-delay minutes per arriving flight (destination side). Each is a percentile in the peer set; the congestion index is their weighted mean (`congestion` weights, renormalized when one is missing) and is then ranked in the peer set like every other component, so all components have the same spread and the 0.25 weight means what it says (a mean of percentiles is squeezed toward the middle). Cancellations are shown, never scored. On-Time covers only the large reporting carriers: an airport with fewer than `min_ontime_flights` scheduled On-Time departures in the window (or none) has no congestion and is scored on the rest, with medium confidence. Before On-Time is loaded, congestion is unavailable for everyone and the weights are renormalized.
- Growth = passengers in the window vs the previous 12 months
- LongHaul = departures >= threshold / passenger-service departures; a share below `long_haul_min_share` (2%) counts as 0 for the percentile, and the true share is still shown
- DemandContext = population growth of the CBSA (metropolitan or micropolitan area) the airport lies in: ACS 5-year population (B01003_001E) in `census.vintage` (2024 = 2020-2024) vs `census.base_vintage` (2019 = 2015-2019), the previous non-overlapping 5-year period; CBSA from the airport's coordinates (Census Geocoder, `airport_cbsa`). Airports in one CBSA share the value (LAX and SNA). Population level is shown, not scored (scale already measures size). No CBSA (7 peer airports in 2025: BET, GUM, SCC, SIT, SPN, STT, STX) or a CBSA code missing in the base vintage (delineation changed) -> missing for that airport: renormalized, medium confidence. Census not loaded, or no airport geocoded -> unavailable for all, weights renormalized. Card: `airport_metrics` topic `demand` (and `all`) adds the CBSA, its population, the growth and the percentile; `rank_airports` adds it to the weights used, the per-airport summary and the drivers.
- Why Scale: profit depends on volume as well as pressure. Without it a small airport with fast growth outranks a large one (HVN +25% on 0.7M passengers vs BOS on 21M).
- Why LongHaul is only 0.10: it hints at wide-body and international facilities, but it is secondary and distorted by cargo.
- Why the 2% long-haul floor: without it, 55 peer airports with 0% tie at the bottom while airports with a few charters (about 0.1%) reach the 65th percentile; noise, not a facility signal.
- Missing component -> renormalize weights, lower confidence, say so.
- Question mapping: Q2 = Congestion; Q3 = LongHaul; Q4 = Utilization + Congestion + delay causes + spill proxy.
- Confidence (deterministic): high = all components, full 12 months, in the peer set; medium = a component renormalized or partial coverage; low = fewer than 12 months in the window (`scoring._confidence`). Unmet demand is capped at medium.
- Rank stability (`scoring.rank_stability`, in every `rank_airports` result): `sensitivity.runs` (20) runs; in each, every weight the ranking used is multiplied by (1 + u), u uniform in +/- `weight_jitter` (25%), drawn with numpy's generator seeded by `sensitivity.seed` (42), then renormalized; scores are recomputed from the same percentiles (`weighted_score`, shared with `score`) and the region re-ranked (ties by IATA). Per airport: share of runs in the top `top_n` (3), runs ranked first, min and max rank; shown as two ranking-table columns and in each airport's summary fact, with a method fact and "Stability of the top airport". If the score's #1 is first in fewer than `stable_share` (90%) of runs, the headline adds "Not stable: ...". Same seed, same output (tested). It tests sensitivity to the weights, not to the data.

## Agent and UI
- LangGraph ReAct agent built with `create_agent` from `langchain.agents` (`langgraph.prebuilt.create_react_agent` is deprecated since LangGraph 1.0; same engine) with a checkpointer and `thread_id` for follow-ups. System prompt: scope rules, assumptions policy, clarify when ambiguous, reply in the user's language.
- Output check: `ensure_facts` (see Tools and envelope) appends required facts the answer omits; no retry loop.
- Commentary figure check (`src/figure_check.py`, applied in `AirportAgent.ask` after `drop_restated_headlines`, before `ensure_facts`): every number in the commentary must appear in a tool envelope of the conversation (all turns, so follow-ups may quote earlier cards). Formatting is tolerated (81.6 %, 81.6%, thousands separators, "2.7 million"); a value matches if it rounds to the precision written (81.58 supports 81.6 and 82); values below 1 also count as percentages. Ignored: years, periods (2025-01), numbers glued to letters (T-100, A320, 2nd) and whole numbers up to 12 without % (counts, months). Also removed: a compare_airports figure plainly credited to the wrong airport (in the other airport's facts and not in this one's; credited only when the number follows its airport with no comma, "and", "vs", "than" or similar in between, or is followed by "at/for <airport>": unclear cases such as "its 19.2% versus 18.1% at LAX" are not judged, after the first eval run showed false positives), an airport name next to a code that is another airport's name in the envelopes ("Bradley (BTV)"), known misreadings ("X% of long-haul flights"), and dates the data does not cover (P5.9b, `period_problems`): a month range must be one of the envelopes' data periods ("January to December 2025", "2025-01..2025-12"; "Mar 2025 - Dec 2025" is removed), a single month or year must lie in one or be named in the envelopes (peak months, the upstream month in a freshness note). Whole sentences are removed; if nothing is left, the commentary is a fixed note ("withheld because it contained figures that are not in the data"). The removed sentences and reasons are in `Reply.figure_check`, shown as a caption under the commentary (app) or after it (CLI). The data card is never changed.
- Commentary mode per tool (P3.8b): the figure check verifies that numbers exist, not that an ordering or a direction is right (the first eval run rewrote the New England ranking with real figures, and a rerun called LAX's longer taxi-out "shorter"). When a turn calls a tool in `commentary.restricted_tools` (config/weights.yaml: `rank_airports`, `compare_airports`), `restrict_commentary` replaces the figure check: it keeps only sentences with no digit, no airport code and no airport name or distinctive name word from the envelopes ("Bradley", "Burlington"; the excluded airports of a ranking count too: `excluded` entries carry `iata`, `name` and `reason`), and drops tables, headings and rules. What is left is caveats and next-step suggestions; the card and headline carry the result. If nothing is left, the app shows no commentary block and the CLI says the card is the answer (no "withheld" note, no fallback message). The prompt asks for at most two such sentences after these tools. Other tools keep the figure check. `scripts/eval.py` does not count restricted-mode removals as failures.
- Turn guard (`turn_guard` middleware around every model call, src/agent.py): (1) tool results from earlier turns are sent in compact form (headline, facts, period, confidence; the facts include one line per ranked airport), so follow-ups like "which of these has the highest load factor?" work from the earlier card without filling the context; the checkpointer and the `Reply` keep the full envelopes. Finding (P2.14): ToolMessages were never dropped by the agent, but a New England ranking is about 2,100 tokens, so two or three turns overflowed Ollama's default context and Ollama silently cut the oldest messages. (2) An empty reply (no tool call, no text after `<think>` stripping) is retried once with a short nudge that is not stored; if still empty, the commentary is a fixed message, never blank. (3) With `OLLAMA_NUM_CTX` set, a warning is logged when the estimated prompt (4 characters per token, system prompt, messages and tool schemas) reaches 80% of it.
- Data first, commentary second: `src/render.py` (pure functions) turns each envelope into markdown: a facts card (label, value; required facts marked), the ranking table (rank, airport, name, score, passengers, load factor, growth, confidence), the excluded airports with reasons, and the assumptions. Numbers and rankings shown to the user come from this code, never from the model text. The agent returns a `Reply` (tool calls, envelopes, the model's `commentary`, and `text` = commentary plus the `ensure_facts` footer for text-only use). The CLI and the app print the rendered data, then the commentary labeled as such; since the card already shows every fact, they show the commentary without the footer.
- Streamlit chat (`app.py`). Each answer has three parts, in this order: "Data (from tools)" rendered by `src/render.py` from the envelopes (excluded airports in a collapsible section), "Commentary (model)" with the model's text, and a collapsible "Tools called" with the raw calls and envelopes as JSON. Sidebar: data period, freshness, provider and model name (never keys), the Census attribution, a "New chat" button (new `thread_id`) and the four exam questions as sample buttons. A missing model or database shows the `ConfigError` message, not a traceback. UI strings in English; RTL is out of scope. Streamlit reruns the script on every message, so the agent and its memory live in `st.cache_resource` and the `thread_id` in `st.session_state`. SQLite is opened read-only (`mode=ro`) per call. Voice is a stretch goal (`st.audio_input`).

## Evaluation (P3.7b, not in CI)
`scripts/eval.py` runs `eval/questions.yaml` (id, question, optional thread `group` for follow-ups, expected `tools`, `must_have` fact labels, `must_not` text) through `build_agent` with the normal `.env` settings, a fresh thread per group. Per question it appends one JSON line to `eval/results/<timestamp>-<model>.jsonl` at once: tools called, seconds, commentary, figure-check result, empty or cut-off flag, expected-tool check, missing facts and pass/fail (pass = expected tools called, or none when `tools: []`; must-have facts present; nothing forbidden written; no sentence removed by the figure check; not empty or cut). It prints a markdown table; `--report` re-renders a saved file, `--only` and `--out-dir` select questions and folder. It is the model-comparison tool: change the model in `.env` and rerun.

## Known limits of the score (observed on real data, 2025 window)
- The passenger floor is a policy line, not a fact: PSM (85,102 passengers) is excluded just under the 100,000 floor. The floor is in `config/weights.yaml` and the excluded list states the reason for each airport.
- Long haul separates only the big hubs: 201 of 233 peer airports have no material long-haul share, so the component mainly adds a bonus for about 30 hubs (BOS in New England). It stays at 0.10 for that reason.
- Exact score ties occur (19 of them) when all components are equal; they are broken by IATA code and should be reported as ties.
- Scores are relative to the peer set, so adding or removing airports moves the percentiles. The rank-stability check (P3.5) shows how sensitive the ranking is to the weights: before congestion was scored, the scenario `weights={"growth": 0.30}` moved PWM to first and BOS to third in New England; with congestion (P3.2) the same scenario keeps BOS, BTV, BGR as the top 3.
- On-Time coverage: 15 of 233 peer airports have no congestion value (2025): 2 with no flights of the reporting carriers (HVN, ILG) and 13 under `min_ontime_flights` (e.g. GUM, 968,896 passengers but 732 reported departures; ORH 962). HVN (seventh in New England once demand_context is scored, P4.3) is therefore scored without congestion.

## Model comparison findings (lfm2.5:8b vs gpt-oss:20b, 2026-10-10)
Same questions, same data, `OLLAMA_NUM_CTX=16384`, temperature 0, local Ollama on the development laptop.
- Earlier UI testing (before P2.9c-P2.14): with both models the data cards were correct. The gaps were in the tools and the agent: answers to "which of these has the highest load factor?" depended on the model sorting numbers, scenario weights were re-weighted by the model in prose, "California" and unknown names gave bare errors, a passenger question showed long-haul rows, and an empty reply produced a blank commentary.
- Design, now fixed in code and the same for any model: the headline and every figure (tools), sorting by a metric and scenario weights (`rank_airports`), match ranking, no-match suggestions and unsupported regions (`resolve_airport`, `rank_airports`), rows per topic (`airport_metrics`), compact history, empty-reply retry and fallback (`turn_guard`).
- Still model-dependent: which tool and arguments the model picks (topic, `sort_by`, `weights`), whether it asks on ambiguity, and the quality of the commentary. These stay checked by tests with a scripted model only; P2.10 measures them on real models.
- Latency, seconds per turn (agent loop incl. tool calls; a 13-of-16 run, stopped before the last three gpt-oss questions; tool choice and commentary were not recorded in this run):

| Question | lfm2.5:8b | gpt-oss:20b |
|---|---|---|
| New England expansion candidates | 126 | 258 |
| Follow-up: highest load factor among these | 121 | 58 |
| Follow-up: what if growth weighs more | 99 | 172 |
| Long-haul share out of Anchorage | 70 | 70 |
| SFO passengers | 57 | 59 |
| California ranking (unsupported region) | 110 | not run |
| Load factor at Portland (ambiguous) | 70 | not run |
| LA vs Santa Ana congestion (no congestion data) | 105 | not run |

- Reading: both models take about one to four minutes per turn on this machine, so latency comes from the hardware and model size more than from the tools; gpt-oss:20b is slower on multi-step turns (ranking, scenario) and similar on single-tool turns. The eval harness (P3.7b, `scripts/eval.py`, which replaced P2.10) records tool choice, faithfulness and latency per question.
