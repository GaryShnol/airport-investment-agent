## Working agreements
- Build in vertical slices: after M2 the app already answers questions end to end; later milestones add data and depth.
- One branch per milestone or slice (`m2-vertical-slice`, `m3a-ontime-congestion`), merged into `main` by pull request. `main` stays green: CI runs `pytest`.
- Commit per task, message prefixed with the task id (for example `P2.2: T-100 ingest`). Tick the task here in the same commit.
- Tests first for scoring. No hardcoded values: `.env` through `src/config.py`, methodology in `config/weights.yaml`.

## Decision log (for the interview)
| Decision | Why | Trade-off |
|---|---|---|
| LLM never computes numbers; tools return an envelope | Trust and auditability, exam requires deterministic scoring | More code than letting the model reason over tables |
| LangGraph prebuilt ReAct agent on `langchain-core` models | The job post names LangChain-family frameworks; memory by `thread_id` comes free; no custom graph needed for one agent and six tools | A framework dependency; a manual tool loop would be about 60 lines |
| SQLite with pre-aggregated tables and a prebuilt seed DB | Runs offline in seconds, reproducible for the reviewer | Data frozen until `ingest` is rerun |
| Seed DB as a gzipped GitHub Release asset with a sha256, downloaded by `src.bootstrap` on first start (not committed) | The aggregated DB is about 35 MB; keeping binaries out of git keeps the repo small and its history clean, and a release pins one data version per URL. Checksum, temp file and atomic move mean a failed download never leaves a half-written DB | First start needs the network once (or a mounted DB, or `ingest` with raw files); a new data version means a new release and a new `SEED_DB_URL` |
| Ingest is offline and idempotent, with `--check` | Chat stays fast and stable; freshness is measured, not guessed | No live data in chat |
| One analysis window (trailing 12 months, `min(last_period)`) | Consistent across sources, easy to explain | Newer months wait for the slower source |
| Stale means upstream has a newer month | Honest (publication lag is about 2 months) | Needs the network once to know |
| Provider registry in `src/llm.py`, selected by `.env`; local Ollama model by default, OpenAI ready but commented out | Free and offline for development and for the reviewer's first run; OpenAI is one uncommented key away, no code change | Local models call tools less reliably |
| Methodology in `config/weights.yaml`, infra in `.env` | Reviewable and versioned vs per-deployment and secret | Two config sources, one loader |
| Score is a capacity-pressure proxy, not a terminal-need measure | No gate or terminal-area data in public sources | Stated as a limit in every answer |
| Congestion = delay rate, taxi-out, NAS delay per arriving flight; cancellations not scored | Carrier delay is airline-driven, cancellations are mostly weather | Fewer signals |
| Census kept (10%), built after the vertical slice; FAA NAS Status dropped | Census works with a key; FAA is live status only, no history | Needs an airport-to-CBSA mapping (Geocoder, cached) |
| Replies in the user's language, English default | Global reviewers; Hebrew works too | None |
| Six small tools | Reliable tool choice, also for local models | Less flexible than free-form SQL |
| Scale component (0.15) in the score | Profit depends on volume, not only pressure and growth; stops tiny fast-growing airports from topping the ranking | One more weight to defend (it is in YAML and covered by the stability check) |
| Passenger service = config 1 or 3, peer set = US airports above a passenger floor (100,000/yr; a departure floor admitted 9-seat commuter airports) | One explicit definition shared by ingest, scoring and tools | Acceptance values must be re-baselined once |
| On-Time split into origin and destination sides | BTS records delay causes for arrivals; mixing sides would misattribute them | Slightly wider table |
| UI shows the data rendered from tool envelopes first, the model text second as commentary | Numbers on screen never depend on the model copying them; the model's text is clearly labeled | Some repetition when the model restates figures |
| Agent in `st.cache_resource`, SQLite opened read-only per call | Streamlit reruns the script per message; keeps memory and avoids thread errors | None |
| Scenario weights in `rank_airports(weights=...)`: keys given replace the configured weight, the others keep it, then all are renormalized over the built components; validated against `config/weights.yaml` keys, non-negative; result labeled "scenario" with base rank next to scenario rank | "What if growth weighs more?" is answered by the scoring code, not by the model re-weighting numbers; "growth 0.30" reads as "growth 0.30 instead of 0.15, all else as configured", the simplest rule to explain; the base rank keeps the configured methodology visible | Values need not sum to 1, so 0.30 is not the final weight (here 0.375 after renormalizing); the envelope shows the weights actually used. Defaults stay only in the YAML |
| `min_ontime_flights: 1000` scheduled On-Time departures in the window to score congestion | On-Time covers only large reporting carriers. Peer-set delay rates have an interquartile range of 17.5% to 22.3% (4.8 points); at 1,000 flights the 95% margin on a 20% rate is about 2.5 points, at 365 flights (one a day) about 4.1 points, as wide as the whole range. 1,000 is about three reported departures a day | 13 of 233 peer airports lose congestion (scored on the rest, medium confidence), including GUM (969k passengers, 732 reported departures) and ORH (962) |
| Congestion index = weighted mean of the three sub-metric percentiles, then ranked again in the peer set | Same scale as every other component; a mean of percentiles is squeezed toward the middle, which would quietly give congestion less than its 0.25 | The final value is a percentile of an index, one step more to explain; the sub-percentiles are shown in the card |
| On-Time ingest keyed by file sha256; previous-window coverage checked only for T-100 | A republished month reloads alone, a rerun reads nothing; On-Time has no 2024, which must not switch growth off | Hash column in `ingest_log`; T-100 keeps month-based idempotency |
| Cancelled flights in On-Time: counted as scheduled departures (cancellation rate), never as arrivals; empty delay or taxi-out fields are skipped (empty is not zero); the 4,285 cancelled flights with a departure-delay value and 693 with a taxi-out time (2025) are kept as reported, not zeroed or dropped. Column definitions: `ontime_airport_month` in the SQLite schema of `docs/plan.md` | BTS fills these fields only when the event happened (e.g. pushback before a cancellation); zeroing would invent on-time flights, dropping would discard real delays. The delay rate divides by `dep_del15_n` (departures that report DEP_DEL15), so it stays consistent either way | A few cancelled flights add to the delay and taxi-out figures (0.06% of 2025 flights) |
| On-Time source format: the ingested files are TranStats custom downloads (`T_ONTIME_REPORTING.csv`, upper-case columns such as `DEP_DEL15`); `CLAUDE.md` and `docs/plan.md` (Traps, `--download`) still describe the PREZIP files, which use different column names. Decided in M4: ship a prebuilt seed DB (P4.5, P5.1); reading PREZIP waits for `--download` (P4.6) | The custom downloads were already on disk and carry exactly the needed columns; the decision depends on how M4 refreshes data (P4.3-P4.5) | Until M4, a PREZIP file dropped into `data/raw/ontime` would fail the column check instead of loading |
| Significance in `compare_airports`: 95% margin per On-Time figure (rates from flight counts, minute averages from the spread of the 12 monthly means); a difference inside the combined margin sqrt(m_a^2 + m_b^2) is "no meaningful difference", never a winner; T-100 figures compared as is | On-Time covers only the large reporting carriers, so its flights are a sample of the airport's traffic; T-100 counts every flight, so its differences are exact. Real result: LAX vs SNA NAS delay per arrival 1.97 vs 1.76 min is inside the margin (about 0.28 and 0.25), so no winner is named | The binomial margin assumes independent flights (delays cluster by day and weather, so it is optimistic); the monthly margin also absorbs seasonality (conservative). Both are stated in the assumptions |
| Unmet demand as a labeled proxy: passengers above the target load level (the excess over 0.80 x seats), per route and month, with a 0.75-0.85 range; confidence capped at medium | T-100 only records passengers who flew; turned-away demand is invisible without booking or spill data. Loads above about 80% are where airlines start to spill passengers, so the passengers above that load level (the excess over 80% of seats, not every passenger on a full flight) mark where capacity is tight. Per route and month so that a full June on one route is not averaged away by a quiet January. SFO 2025: 10 of 12 months above 80%, 1,427,569 passengers above the line (5.4%), range 2.6M at 75% to 0.56M at 85% | It undercounts true spill (people who never got a seat do not appear) and depends on the target, hence the range; it says where demand presses, not how much is lost |
| Rank stability by seeded weight perturbation: 20 runs, each weight x (1 + u), u uniform in +/-25%, renormalized; per airport the share of runs in the top 3 and the min/max rank; a headline note if the #1 is first in under 90% of runs | Answers "would a slightly different methodology change the answer?" with numbers instead of an argument; seeded so the same question gives the same card. Uniform relative jitter keeps every weight positive and roughly in proportion; recomputing from the stored percentiles makes 20 runs cost milliseconds. New England 2025: BOS, BTV, BGR are top 3 in 100% of runs; PWM never enters the top 3 (always 4th); HVN, BDL, PVD swap places 5-7 | It covers the weights only, not the data, the peer-set floor or the component definitions; +/-25% is a choice (in the YAML) |
